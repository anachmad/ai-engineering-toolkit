# Policy and manifest contracts

All policy and project manifest files currently use JSON syntax, which is a subset of YAML. Arbitrary YAML is not supported. `schemas/policies-v1.json` defines machine-readable top-level fields and types; deeper path and cross-file checks are implemented in Python. Each file has an integer `schema_version`; the implementation supports version 1 and rejects other versions without changing files. This document describes version 1; incompatible versions require a separately reviewed migration.

- `profiles.yaml`: `schema_version`, `default_profile`, three named `profiles`, and nonempty `escalation_factors` are required. Each profile contains `artifacts` and `conditional_artifacts` lists of safe relative paths. Optional `scaffold_files` maps safe output paths to templates under `templates/project`.
- `quality-gates.yaml`: version 1 has the same three profile names. Each contains nonempty `requirements`, `code`, `security`, `qa`, `operations`, and `release` descriptions. These descriptions are not automated enforcement.
- `document-prompts.yaml`: version 1 maps safe document paths to nonempty lists of nonempty section prompts. Each configured documentation artifact needs prompts.
- Project manifest: `schemas/project-v1.json` is the versioned declarative contract for required fields, types, minimum text, and enumerated values. The standard-library validator implements this project's small contract vocabulary, not general JSON Schema. Unknown manifest fields are permitted and preserved by UI updates.

A relative `standards_path` is relative to the project root; an absolute path refers to that exact directory. Audit and manifest updates require the directory to exist and resolve to the standards directory of the toolkit performing the operation. A missing or different location stops the command for review. There is no silent migration or automatic policy switching. A project that moves with its own `.engineering/toolkit/` and a relative standards path remains portable. A shared toolkit copy's `provenance.json` records SHA-256 hashes of copied bytes, including uncommitted source changes; it does not assert a Git revision, approval, or a managed update.
